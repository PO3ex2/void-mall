# Void Mall — Архитектура

> Unity **6000.6.4f1**, URP 17.6, Input System 1.20. Геймдизайн — `GAME_DESIGN.md`, этапы — `ROADMAP.md`.

---

## 1. Ключевые решения

| Тема | Решение | Почему |
|---|---|---|
| Сеть | Одиночная игра = **локальный хост**. Сетевая абстракция есть с первого дня, библиотеку (FishNet или NGO + Steam-транспорт) подключаем на этапе коопа | Не тормозим разработку, но и не загоняем себя в угол |
| Авторитет | Хост отвечает за мир, лут, ИИ, урон и инвентари. Клиент отвечает за **своё движение** (owner-authoritative). **До 16 игроков** | Кооп с друзьями: читерство не критично, отзывчивость важнее |
| Данные мира | **Единая сетка 1 м**: у клетки есть материал, плотность и повреждение. Блоки мешатся кубами, гладкие воксели — Surface Nets | Одна система коллизий, сейвов и сети |
| Вычисления | **GameObjects + Jobs + Burst** (Unity.Collections, Unity.Mathematics) | Скорость Burst там, где нужна, и простота MonoBehaviour в остальном |
| Мир | Бесконечен по XZ, **высота 128** (фундамент, 2 уровня парковки, 5 торговых этажей, технический этаж, кровля) | Колонны чанков, простой стриминг |
| Целостность | **Упрощённая**: обрушиваются только острова клеток, не связанные с опорой | Дёшево, понятно игроку, без расчёта нагрузки |
| Планировка | Иерархия: **разделы (Вороной) → комнаты → шаблоны → лут → аномалии** | Детерминизм по сиду, контроль над разделами |
| Контроллер | **Свой кинематический** collide-and-slide на CapsuleCast, физика в духе Source | Полный контроль, готовность к предсказанию по сети |
| UI | **UI Toolkit везде**, ПК — world-space UIDocument | Навигация с геймпада, один UI консоли для ПК и оверлея |
| Лобби → мир | **Настоящий портал**: вторая камера рендерит вид мира, при пересечении игрок телепортируется | Бесшовно, одно лобби на все миры |
| Сейвы | **Все посещённые чанки целиком** в бинарных файлах-регионах со сжатием, метаданные в JSON | Надёжно при смене версии генератора |
| Данные контента | **ScriptableObjects + реестр со стабильными строковыми ID** | Удобно в редакторе, стабильно в сейвах и по сети |
| Ввод | Input System, схемы **KB&M + Gamepad сразу** | Требование |
| Рендер | URP **Forward+**, GPU Resident Drawer, GPU occlusion culling | Много ламп и пропов в процедурном мире без запечённого окклюжена |

### 2.1 Зависимости сборок (asmdef)
Направление строго сверху вниз, циклов нет:
```
Game ─┬─> Lobby, UI ─┬─> Console
      │              └─> Player, Items, Crafting, Survival, Skills, Combat, AI, Props
      ├─> Save ──────> World, Items, ...
      └─> World.Gen ─> World ─> Net ─> Core
Player ─> Input, Console, Core   (о Survival и Items мотор знает только через интерфейсы из Core)
Console ─> Core                  (низкоуровневая: команды объявляются в любой сборке атрибутом)
```
Связь между модулями идёт через **интерфейсы в Core** и **события**. Например, `IMovementModifierSource` реализуют Items (вес) и Survival (травмы), а мотор их только опрашивает.

## 3. Ядро (Core)

- **Composition root** — `GameBootstrap` в сцене Boot создаёт сервисы и регистрирует их в `Services` (простой локатор, без стороннего DI). Сервисы — обычные C#-классы, MonoBehaviour только там, где нужен жизненный цикл Unity.
- **Тики:** `Time.fixedDeltaTime = 1/60`. Симуляция (мотор игрока, пропы, ИИ, крафт-таймеры, статусы) работает в фиксированном тике, рендер и камера интерполируются.
- **События:** типизированная шина `EventBus<T>` (struct-события, без аллокаций) для слабосвязанных реакций — «приземлился», «блок сломан», «предмет подобран».
- **Реестры контента:** `Registry<TDef>`, где `TDef : ContentDef` (ScriptableObject с полем `string Id`, например `"item.food.canned_beans"`). При запуске каждый ID получает числовой runtime-индекс. Таблица соответствия ID ↔ индекс пишется в сейв и передаётся клиентам при подключении. Редакторный валидатор проверяет уникальность ID и битые ссылки.
- **Детерминированный RNG:** собственный `Rng` (xorshift/PCG) и `Hash(seed, x, y, z, salt)`. `UnityEngine.Random` в генерации **не используется**.

## 4. Мир

### 4.1 Координаты и чанки
- Чанк — **32×32×32 клетки**. Колонна — 4 чанка по вертикали (высота мира 128). **Колонна — единица стриминга и сохранения.** Пустые и однородные чанки (воздух над кровлей, сплошной фундамент) почти ничего не стоят.
- Вертикальный разрез задан в `MallLayoutConfig` (SO): фундамент 0–7 (слой 0 неразрушаем), P2 8–12, P1 13–17, этажи 1–5 по 7 блоков (18–52), технический этаж 53–59, кровля 60. Количество этажей — параметр конфига (сейчас 5), моддеры могут его поменять.
- Координаты: `int3` клетки мира, `int2` колонны, `int3` чанка. Позиции сущностей в данных хранятся как `(int2 колонна, float3 локально)`.
- **Floating origin:** при удалении игрока больше чем на 2 км от origin все корни сдвигаются. В кооперативе у каждого клиента свой origin, а сеть передаёт абсолютные координаты.

### 4.2 Клетка
```
struct Cell { ushort Material; byte Value; byte Meta; }   // 4 байта
```
- `Material` — индекс в каталоге материалов (0 = воздух). Тип материала — `Block` или `Smooth`. Новые материалы добавляются только в конец каталога.
- `Value` — у блоков **форма** (0 = полный куб; плиты, ступени, скосы — позже), у гладких материалов — **плотность** 0..255 (128 = поверхность). Для Surface Nets блок всегда считается плотностью 255.
- `Meta` — поворот блока (биты 0–4, 24 ориентации) и флаги (биты 5–7).
- **Повреждение** хранится разреженно в чанке (`Dictionary<индекс, урон>`): повреждённых блоков мало, а точность урона нужна полная.
- Чанк: `NativeArray<Cell>` (128 КБ) с пулингом. Полностью пустые или однородные чанки хранятся одним значением.

### 4.3 Мешинг (Burst-джобы)
- **Блоки:** face culling с отсечением граней между непрозрачными блоками, **вершинный AO**, UV в **Texture2DArray** (индекс слоя хранится в UV.z). Greedy-слияние только для граней с одинаковым AO — оптимизация на потом.
- **Гладкие:** **Naive Surface Nets** по полю плотности. Блочные клетки для него — плотность 255, поэтому гладкая поверхность корректно «упирается» в блоки. Материал вершины берётся по ближайшей твёрдой клетке, текстурирование — **triplanar** с Texture2DArray.
- Прозрачные блоки (стекло) — отдельный сабмеш.
- Для бесшовности мешинга чанку нужен «паддинг» в одну клетку от соседей, поэтому джоба получает 3×3×3 окрестность (только чтение).
- Результат пишется в `Mesh.MeshDataArray` → `Mesh.ApplyAndDisposeWritableMeshData`.
- **Коллизия:** `Physics.BakeMesh` в джобе → `MeshCollider` (отдельный упрощённый меш без прозрачных граней).
- **Бюджет:** не больше N завершений мешинга за кадр (настраивается) и приоритет по расстоянию до игрока или направлению взгляда.

### 4.4 Стриминг
- `ChunkStreamer` держит колонны в радиусе `viewDistance` (по умолчанию 8 колонн = 256 м, в помещениях больше не нужно) от каждого игрока.
- Конвейер состояний колонны: `Requested → Loading (с диска) | Generating → Generated → Decorating (пропы, лут) → Meshing → Ready → Unloading (запись на диск)`.
- Отдельный, меньший радиус `simulationDistance`: внутри него пропы, ИИ и физика активны, снаружи — заморожены или выгружены.

### 4.5 Правки мира
- Любое изменение — **команда** `WorldEdit` (SetBlock, DamageBlock, SmoothBrush{center, radius, delta, material}).
- Поток: `инициатор → INetSession.SendToAuthority → WorldAuthority проверяет → применяет к данным → рассылает WorldChanged → у всех ремеш затронутых чанков (и соседей на границе)`.
- В одиночной игре всё это — вызовы в пределах одного процесса.
- Из сломанных клеток выпадают предметы по `MaterialDef.drops`.

### 4.5.1 Упрощённая структурная целостность
- **Опора** — клетки фундамента (нижний слой мира) и материалы с флагом `MaterialDef.isAnchor` (несущие колонны генератора можно сделать прочными, но не якорями — решим на плейтесте).
- После удаления клетки авторитет запускает **ограниченный flood fill** (6-связность, только твёрдые клетки) от каждого твёрдого соседа удалённой клетки:
  - дошли до опоры — кусок держится;
  - перебрали весь кусок в пределах бюджета (`maxIslandCells`, например 4096) и опору не нашли — это **остров**, он обрушивается;
  - бюджет исчерпан — считаем, что кусок держится. Это защита от дорогого расчёта по огромным конструкциям.
- Обрушение: клетки острова удаляются из сетки (одной командой `WorldEdit`), из них строится меш **обломка** с Rigidbody (масса = сумма масс материалов) и упрощённым коллайдером. При ударе обломок наносит урон, разрушается на материалы-дропы и/или пропадает через N секунд.
- Выполняется в Burst-джобе. Стоимость ограничена бюджетом, поэтому на тик не влияет.
- Генератор гарантирует, что сгенерированный мол связан с фундаментом (стены и колонны доходят до перекрытий).
- **Позже (этап 8Е) — воксельные тела вместо обломков:** остров копируется в маленькую сетку `VoxelBody` (до N клеток, клетки 4 байта как в мире) и становится Rigidbody: меш — `ChunkMeshJob` по этой сетке (тот же код форм, текстур, гладких вокселей), коллизия — набор `BoxCollider`, склеенных жадным объединением клеток (MeshCollider у динамического тела не годится), масса и центр масс — по материалам. Попадание луча в тело переводится в координаты его сетки: ломание клетки → перепроверка связности внутри тела (может развалиться на два), постановка блока → клетка в сетке тела (сетка растёт). Синхронизация и сейв — как у пропов (ID, поза, плюс содержимое сетки).
- **Вода (этап 8Д):** `MaterialKind.Liquid` — не твёрдый (нет в коллизии, луч проходит), отдельная подсетка в мешере (верхняя грань чуть ниже края, прозрачный материал); игрок в объёме воды — режим плавания. Вода водных чанков — неразрушима, блок воды — убирается ведром.

### 4.6 Генерация мола (`World/Generation/Mall`)
Каждый проход **детерминирован** и зависит только от сида и координат. Соседние колонны генерируются независимо и в любом порядке (проверяется тестом хешей чанков).

- **Разрез** (`MallLayout`): основание y 0, фундамент 1–7 (гладкий грунт и бетон), P2 и P1 (плита + 3 м + потолок), 5 торговых этажей по 7 блоков (плита + 5 м + потолочный ряд), технический этаж, кровля y 60.
- **Макроячейка 64×64** (чанк 32 всегда целиком внутри одной): вдоль западного и южного края — галереи 14 м с площадью и колонной на пересечении, остальное — квартал 50×50. Неизменные по уровням параметры ячейки (`MallCellInfo`): поворот квартала (×4), положение ядра, атриумы в галереях, пандус парковки, аномалия, маркеры.
- **План уровня** (`MallPlanner.BuildLevel` → `MallLevelPlan`: плитки 64×64, номер комнаты, список комнат). Квартал описан канонически и поворачивается. Ядро (лестничная клетка с двумя маршами, лифтовая шахта, щитовая) одинаково на всех уровнях — вертикальная связность гарантирована. Полосы магазинов у фасада с ядром + северная часть, нарезанная BSP; в каждой стене-разрезе — дверь, поэтому все комнаты связаны (тест обходом). Комнаты у фасада получают витрину (стекло, вход 2–4 м) или рольставню (небольшие закрытые магазины), остальные — подсобки. Атриум: пустота через этажи 2–5, эскалаторы «ножницами» в двух полосах, ограждение открыто только у концов эскалаторов. Парковка: сетка колонн, разметка, пандус P2→P1 с проёмом и отбойниками. Технический этаж — служебные комнаты и коридоры.
- **Разделы** (`SectionDef` + `SectionTable` для Burst): раздел комнаты — по ближайшей точке Вороного на сетке 32 м, взвешенный выбор с маской этажей; с вероятностью 40% этаж повторяет раздел этажа ниже. Служебные разделы выбираются по весам для типа этажа (`SectionDef.ServiceWeightRetail/Tech/Parking`): подсобка — торговые этажи; вентиляционная — технический этаж; щитовая — служебная комната ядра на парковке (всегда), ~11% подсобок и ~6% комнат техэтажа. Под потолком (верхний ряд свободной высоты, мимо ламп) генератор ставит воздуховоды (`block.duct`) и кабельные лотки (`block.cable_tray`): вдоль обеих галерей техэтажа, воздуховод в вентиляционных, лоток в щитовых. В щитовой — главный распределительный щит (место будущего рабочего щитка, этап 8А/12А), электрощиты по стенам, стеллаж с электрикой (свой лут), кабельные барабаны.
- **Геометрия** (`MallGenerationJob`, Burst): по плитке и ряду внутри уровня — плита, стены, витрины, двери с перемычками, потолок, лампы (сетка 4 м, аварийные вдоль фасадов и на лестницах, тёмные комнаты без ламп). Список ламп чанка отдаётся `ChunkManager` для освещения.
- **Аномалии** (`MallAnomalies`, одна геометрическая на ячейку): Бездна — оболочка вдоль SDF «пол → кромка → вертикальная шахта», прорезает все уровни ниже до пустоты; Котлован — скруглённая чаша в полу, 13–30 м в поперечнике, всегда внутри квартала; размер бездны — от ~15 до ~73 м (чаще небольшие). Бездна шире квартала (шахта > 13 м) — только в узлах решётки 3×3 ячеек (`MallPlanner.IsBigAnomalyNode`): она обходит ядра и зоны аномалий окна 3×3, а соседние ячейки получают её во второй слот `MallCellInfo.HasBigAbyss`/`WithBigAbyss()` (своя аномалия остаётся) — генерация, пропы и структуры (эскалаторы, пандусы — `StructureFactory.Blocked`) учитывают её как свою; Вырез — колонна 32×32 от потолка уровня до дна мира. Оболочка толщиной 2 м (плита + потолочный ряд уровня ниже, стык с блочным потолком без ступеньки; тоньше — вершины Surface Nets прилипают к блокам за оболочкой). Облицовка — гладкий двойник пола комнаты (`MaterialDef.SmoothVariant`: ковёр, плитка, терраццо, паркет…), стенки шахты глубже кромки — бетон. Над полом в зоне воздух хранит плотность поля — край плавный. За оболочкой остаётся обычный мол. Маркеры Искажения и Глитча геометрию не меняют.
- **Структуры** (`StructureFactory`, главный поток, по макроячейкам в радиусе прогрузки): марши (визуальные ступени + наклонные коллайдеры), лифт (`ElevatorCar`: положение — функция времени, двери шахты), эскалаторы (`Escalator` — движущаяся поверхность), пандус. Пересекающие вырез не создаются.
- **Мебель** (`PropPlacer` → `PropSpawn`, `MallStructures`): шаблон раздела раскладывает заглушки без пересечений и вне аномалий; «корзины» (ячейка + уровень) грузятся в радиусе `world_prop_radius` на этаже игрока ±1, объекты из пула. На этапе 5 заглушки станут физическими пропами с лутом.
- **Превью** (`LayoutPreview`): только проходы 1–2 → `Texture2D`, 1 пиксель = 1 м (карта F6, позже World Generator в лобби).
- Версия генератора (`generatorVersion`) будет писаться в сейв (этап 9).

### 4.7 Рендеринг мира
- URP Forward+, вершинный AO блоков, SSAO. Шейдер блоков со своими проходами глубины и теней (смещение вершин «Искажения» совпадает во всех проходах).
- Лампы — светящиеся блоки: эмиссию считает шейдер по `LampRules.hlsl` (копия `LampRules` на C#). Настоящие `Light` — пул у ближайших `r_lamplights` горящих ламп с плавным появлением, тени — у `r_lampshadows` ближайших.
- Структуры и мебель — процедурные меши с цветом вершин и одним материалом `VoidMall/Props` (SRP Batcher).
- «Искажение» — смещение вершин в мировых координатах по объёму-маркеру; «Глитч» — подмена текстур блоков, сдвиг полос, развёртка; пульсация и рябь «Смотри на меня» — тоже смещение вершин (§4.11). Объёмы задаёт `AnomalyFxDirector`.

### 4.8 Время суток и освещение
- `WorldClock` (сервис `IWorldClock`, авторитетный) — игровое время, длительность суток из `WorldSettings` (`time_daylength`).
- Состояние лампы нигде не хранится — оно выводится из сида, клетки и времени (`LampRules`): группа ламп = макроячейка на уровне. С 22:00 до 23:00 группы гаснут волной (у каждой своя фаза, на переходе мигают), с 6:00 до 7:00 включаются. 12% групп мертвы всегда (участки тьмы), 5% ламп мёртвые, 8% нестабильные. Аварийные лампы горят только вечером: загораются по одной с 19:45 до 20:00, с 23:30 каждая гаснет в свою фазу (мигая) — к полуночи тьма полная (`LampRules.EmergencyWave`, `_VM_EmergencyWave`); световые фонари атриумов следуют за солнцем.
- `LightingDirector` назначает пул источников, меняет ambient (включая пробу SH), отражения и туман по времени суток. Небо камера не рисует: фон — цвет тумана (даль за прогрузкой растворяется в дымке, конец тумана — не дальше края прогрузки); туман темнеет вечером вместе со световыми фонарями и чернеет с отключением ламп.
- **Освещённость в точке** (`ILightProbe`, для рассудка и Манекена): вклад ближайших горящих ламп с затуханием, рейкаст заслонения для трёх сильнейших, плюс динамические источники игрока (`LightingDirector.DynamicLights`) и ambient. Рендер с GPU не читается.

### 4.9 Функциональные блоки и шаблоны формы (этап 8А)
Четвёртый тип геометрии рядом с блоками, вокселями и пропами.
- **`FunctionalBlockDef`** (SO): размер в клетках (1×1×1, 1×2×1…), модель (меш или префаб), коллайдер-коробки, прочность и что выпадает, компонент функции (дверь, конвейер, щиток, генератор…). Физики нет.
- **В сетке:** отдельный «материал» функционального блока. Клетка-якорь хранит индекс определения и поворот (`Meta`), остальные клетки объёма — ссылку на якорь (смещение в `Value`/`Meta`). Удар по любой клетке ломает блок целиком; поставить можно, только если весь объём свободен. Структурная целостность считает функциональный блок обычным твёрдым.
- **Рендер и коллизия:** блок-мешер такие клетки пропускает; модели рисуются инстансами по чанку (как товары на полках), коллайдеры — простые коробки в чанке. Состояние (дверь открыта, конвейер работает) — в разреженном словаре чанка по якорю, сохраняется вместе с правками.
- **Функции:** компонент-логика по якорю (`IFunctionalBlock`: `Interact`, `Tick`), тикает только в загруженных чанках; питание и конвейеры — граф устройств поверх них (этап 12А).
- **Шаблоны формы:** блок с формой (ступенька, скос, четверть…) хранит форму в `Meta`, материал — как обычный блок. Пустой шаблон ставится предметом, ПКМ блоком по нему задаёт материал. Мешер берёт геометрию формы из таблицы шаблонов (повернутую по `Meta`), коллизия — по тому же мешу.

**Реализовано (этап 8А):**
- Функциональный блок — материал вида `MaterialKind.Functional` (`fblock.door` 1×2×1, `fblock.gate` 1×3×1, `fblock.sliding_door_1|_2|_4` — 1×3×1, 2×3×1, 4×3×1) с `Function` и `FunctionalSize` в `MaterialDef`/`MaterialInfo`. Клетки: `Value` — смещение до якоря (dx 3 бита, dy 3, dz 2), `Meta` — поворот (биты 0–1), у якоря ещё открыт (2), заперт (3), сторона открывания (4) — `FunctionalCells`. Такие клетки не непрозрачны (грани соседей рисуются), мешер их пропускает, `EmbeddedEscape` считает пустыми, луч `VoxelRaycast` проходит сквозь открытые.
- Генерация (`MallGenerationJob`): двери в части проёмов `Tile.Door`/`CoreDoor` (решает хеш прохода, у двойных петли по краям), ворота на месте `Tile.Shutter` (заперт ли — по хешу начала проёма), автоматические двери в части проёмов `Tile.FacadeDoor` — проём режется на цельные блоки жадно (4, 2, 1 клетка; двух 2×3 рядом не бывает — створки съехались бы в середину), локальная +X блока вдоль проёма; над дверью в проёме высотой 3 — стена. Якоря отдаются списком, как лампы → `ChunkColumn.Anchors`, `ChunkManager.CollectAnchors`.
- `FunctionalBlocks` (на объекте мира): пул моделей по якорям в радиусе `world_fblock_radius`, дверь вращается на петле, ворота уезжают вверх, коллайдер едет с моделью; автоматическая дверь — по створке на клетку (рама + стекло отдельным прозрачным материалом `FBlock_Glass`), половины разъезжаются в стороны, у 4×3 внутренние створки вдвое дальше; открыта, когда любой `WorldViewer` ближе 2,8 м к отрезку двери (одна проверка на блок раз в 0,1 с) — это локальное состояние клиента, авторитет его не хранит, луч проходит в проём по `FunctionalBlocks.IsOpenLocally`; `CellChanged` обновляет состояние сразу.
- Команды: `PlaceFunctionalCommand` (весь объём пуст и без сущностей — `WorldAuthority.CanPlaceFunctional`), `SetFunctionalStateCommand` (ворота — весь ряд; закрыть нельзя на стоящем в проёме); урон по любой клетке копится в якоре и ломает блок целиком (выпадает предмет через `PlacesBlock`).
- Формы: `Cell.Value` у блоков — `BlockShape` (10 форм, с тонкой панелью `Pane` — витрины и стеклянные ограждения), `Meta` биты 0–4 — ориентация 0..23 = направление верха (6) × 4 + поворот вокруг него (`BlockShapes.Meta(up, yaw)`; поворот, затем наклон — только собственные вращения, обход треугольников не меняется). `BlockShapes` строит треугольники для 10×24 ориентаций (призмы по профилю, ушное отсечение торцов, явные углы скоса), грани на границе клетки помечены для отсечения (частично закрывающие — `Cull ≥ PartialCull`, прячутся только за таким же соседом: панель к панели, полублок к полублоку); таблица уходит в `ChunkMeshJob` (`NativeArray`), коллизия — по мешу чанка. Призраки шаблона — `Game/ShapeGhosts` (в сессии), рисуются `Graphics.RenderMesh`; заполнение — `PlaceBlockCommand` с `Shape`/`Meta`.

### 4.10 Биомы и особые места (этап 8Б)
**Реализовано:**
- **Биом** — поле `MallCellInfo.Biome` (`MallBiome`: `Normal`, `Empty`, `AnomalyField`; мутный лес — отдельным значением на этапе 12Б). `MallPlanner.BiomeOf`: Вороной по центрам на решётке 2 ячейки со случайным сдвигом, биом центра — по хешу (≈50% пустые, ≈40% обычные, ≈10% поле), пятна по 1–6 ячеек. Ячейка старта (`SpawnCell` — первая к востоку без выреза) и её соседи всегда обычные, `NearSpawn` = true. Частота аномалий и маркеров умножается на `BiomeAnomalyMul` (пустые ×0.5, поле ×3.5) внутри `RollAnomaly`, поэтому соседи (бездны узлов, свободный радиус) видят ту же частоту.
- **Пустой биом**: `PropPlacer.Thin` оставляет ~30% мебели комнаты (ряды с прорехами), `ShelfLoot` — ~5% полок с одной находкой.
- **Поле аномалий**: лампы мерцают чаще — `LampRules.FieldFlickerLampChance` на CPU и `_VM_FieldCells` (ячейки поля 3×3 вокруг камеры, `LightingDirector.UpdateField`) в `LampRules.hlsl`. Своей дымки и падения рассудка нет (позже там будут «Смотри на меня»).
- **Вход в мол** (`HasEntrance`: ячейка старта всегда, ~3% ячеек в глубине; первый торговый этаж): поперёк западной галереи (z = 17) — фасад со стеклом и двумя автодверями 4×3 (в проёме галереи двери есть всегда), перед ним турникеты и кассы.
- **Тупики**: поперёк отрезка галереи (`BuildDeadEnds`) — рольставни, витрина со входом в магазин или магазин за рольставнями; магазин — новая комната в плане галереи от фронта до глухого фасада у площади (вдоль 14) или у края ячейки (вдоль 63), раздел ему назначается как витринному; ~10% на полосу и уровень, вдоль 18–28 или 50–60 — не у площади и не поперёк атриума, не у старта; не больше одного на полосу — обе половины остаются связаны со своими площадями). Служебный коридор (`RoomFlags.Corridor`, ~30% торговых уровней): от самого широкого магазина южной полосы отрезаются 2 клетки и стена, вход — проём `Tile.Door` в фасаде, двери разрезов на его боковых стенах заложены.
- **Офисы**: служебный раздел `section.office` (`SectionLayout.Office`, вес в торговых этажах 2.5 — внутренние комнаты без витрины) — сетка столов с мониторами и креслами или, в вытянутых, проход и кабинки с перегородками; шкаф для документов и кулер у стен; свой лут.
- **Круглая площадь** (`MallPlanner.RoundPlaza`, ~25% торговых уровней, половина с фонтаном): узор пола — структура (`StructureFactory.BuildPlazasAndStands`, `MeshBuilder.Ring`), кольцо скамеек и кадок — пропы. Фонтан — блоки мира (`MallGenerationJob.FountainCell`): `block.water` (непрозрачная голубая гладь, пока с коллизией) вместо плиты пола в радиусе 3, бортик — полублоки терраццо до 3.9 (одна клетка, без щелей по диагоналям), в центре 2×2 вместо колонны (план без `Tile.Pillar` на этом уровне) — тумба и «шапка» из четырёх `RoundOuter` вертушкой.
- **Стенд с машиной** (`MallPlanner.CarStand`, ~6% торговых уровней, полоса без атриума, вдоль 36–42): подиум — структура с коллайдером, машина и столбики ограждения — пропы.
- **Заброшенный вид**: поваленный стеллаж (`PropSpawn.Pitch` = −90, `TryAddLying`; его товар `ShelfLoot` рассыпает по полу один раз за сессию), кучи мусора (`prop.trash_pile`) — чаще в пустом биоме, там же мусор в галереях.
- **Техэтаж**: ящики с лутом (`prop.loot_crate`, разбить — таблица «crate» + облако пенопласта `DustFx`), склад стройматериалов (`section.construction`: поддоны с местами под товар, лут — пеноблоки `block.foam_concrete`, доски, мешки цемента). Цемент + крошка на компрессоре дают вдвое больше бетона, доски + гвозди на верстаке — `block.planks`.
- Мебель в рядах и вдоль стен ставится с зазором `PropPlacer.Gap` 4 см: стеллажи вплотную зажимали проснувшегося соседа между спящими (кинематическими) — средний в ряду было не сдвинуть.
- **Балконы** (`MallCellInfo.BalconyX/Z`, ~35% полос без атриума; `MallPlanner.BuildBalcony`): плитки `AtriumVoid` поперёк [4, 10) вдоль [16, 62) с мостиком [37, 41), `Railing` по краю на этажах выше первого — генерация та же, что у атриума (на первом торговом этаже пол, потолок открыт, наверху световой фонарь). На первом этаже пропы можно ставить на пустоту балкона (`PropPlacer.IsFloor`), но не атриума (низ эскалаторов). Тупики и стенды на полосе с балконом не ставятся.
- **Площадь с фонтаном** — на всю ячейку (`PlazaOf`): фонтан на первом торговом этаже (`RoundPlaza(..., out fountain)`), над ним круглый проём (`PlazaWell`, `BuildWell`: пустота радиусом 4.6, ограждение на каждой клетке пола, касающейся пустоты); потолок над фонтаном открыт (`FountainCell`, ряд потолка), колонны перекрёстка нет на всех торговых этажах.
- **Кассы** (`PropPlacer.Checkouts`): витрина с `FacadeDoor` определяет сторону; крупный магазин (площадь ≥ 260 или ряды/склад ≥ 140) — до 6 стоек поперёк выхода с шагом 2.4 и `prop.impulse_rack` за каждой (таблица «impulse»), мелкий — одна касса вдоль фасада. Кассовый аппарат — сама стойка `prop.checkout`: лом + удержание E (`PropInteractor`) → `ShelfLoot.OpenRegister` (таблица «register», один раз за сессию).
- **Технический этаж**: `LampAt` ничего не ставит, автодверей нет (`SlidingDoorCell`); свет — `prop.work_light` (`WorkLightProp`: прожектор-спот, 80% ламп с живым аккумулятором по ID, свет в `LightingDirector.DynamicLights` для освещённости и рассудка; компонент живёт на объекте пула и включается в `PropManager.Spawn`). Ставятся в комнатах техэтажа (70%) и вдоль его коридоров через 16 м.
- **Колонна круглой площади** без фонтана — четыре `RoundOuter`, наклонённые верхом на ±X (ось скоса вертикальна), сплошные углы к центру (7, 7) (`MallGenerationJob.RoundPillar`).
- **Проём лифта** (`CoreDoor` у `ElevatorVoid`) — без функциональных дверей и перемычки; решение о двери в проёме — по его первой клетке (раньше третья клетка проёма в 3 решала отдельно).
- **Рамка и трещины** функционального блока — по всему следу (`ToolController.TargetBounds`), урон — из якоря.
- **Бока ламп**: `MaterialDef.SideMaterial` → `MaterialInfo.SideLayer` — слой текстуры для граней ±X/±Z; у ламп и световых фонарей это потолочная плитка (свечение задаётся по слою, поэтому бока не светятся).
- Отладка: биом в строке `where`/HUD, на карте F6 (пустые блёклые, поле сиреневое), команда `biome` (карта 9×9).

### 4.11 Аномалии 2 (этап 8В)
**Реализовано:**
- **Классы**: `AnomalyNames.Class` — все `AnomalyKind` геометрические, все `AnomalyMarkerKind` визуальные (GDD §2.5, для пылесоса §2.11); там же `Id` (консоль) и `DisplayName`.
- **Маркеры**: до `MallCellInfo.MaxMarkers` = 6 на ячейку (`AddMarker`/`GetMarker`). `PlaceMarkers`: искажение и глитч — как раньше, затем «Смотри на меня» (`LookAtMeCount`: поле аномалий 2–4, обычный мол 12%, пустые 1.5%), пульсация (10% × биом), лужа (12% × биом). Лужа и вспышка — в галерее (`GalleryPoint`), лужа — в полосе у фасадов (поперёк 0…3 или 11…14: посередине бывают пустоты атриумов и балконов), центр лужи — на поверхности пола.
- **Перевёрнутый чанк** (`AnomalyKind.Inverted`, 4% × частота, колонна-чанк через все этажи; не в ячейке старта): `MallGenerationJob` берёт клетку с отражённой высоты своего уровня (`LevelBase + CeilingRow − y`), формы с верхом ±Y отражаются (`Invert`: верх ↔ низ, поворот +2), функциональные блоки становятся воздухом. Пропы — `PropPlacer` отражает позицию (`MallPlanner.MirrorY`) и ставит `PropSpawn.Inverted` (поворот на 180° вокруг горизонтальной оси взгляда). Лампы оказываются в полу — `LightingDirector.LampPoint` ставит источник над блоком. Структуры в колонне не строятся.
- **Оазис** (`AnomalyKind.Oasis`, 12% × частота — самая частая; радиус 3–5.5, центр — в квартале напротив ядра, как у бездны): `TryOasis` — дыра в потолочном ряду торгового этажа, под ней трава (`block.grass`), этажом выше — круглая шахта в бетонной стенке, наверху экран неба (`block.sky_screen`, `LampKind.Screen`: днём светится как световой фонарь, ночью — звёзды-пиксели в `Blocks.shader`; текстура `BlockPattern.SkyScreen` — RGB-субпиксели). Кусты и папоротники (`prop.bush`, `prop.fern`) — `PropPlacer.PlaceOasis`; лианы — меш `StructureFactory.BuildOasis` (кэш по ячейке). `AnomalyVisuals`: прожектор неба (в `LightingDirector.DynamicLights` — место светлое), конус лучей, дождь (`IsRaining`: ~25% игровых часов по хешу ячейки).
- **Физика аномалий** — `AnomalyPhysics` (World): объёмы рядом с игроком собираются раз в 0.25 с (`Refresh` из `AnomalyFxDirector`). Перевёрнутая колонна — гравитация вверх для пропов (`PropBody`) и предметов (`WorldItems`; улёгшийся предмет усыпляется сам). Пульсация (`PulsePeriod` 3 с, фаза > 0 тянет): тела догоняют целевую горизонтальную скорость, ускорение ограничено и падает с массой (тяжёлые стеллажи стоят, лёгкие вещи ездят), действует только на своём этаже. `AnomalyFxDirector` будит спящие пропы в объёме. Игрока сносит `PlayerMotor.ExternalDrift` (без трения и накопления).
- **Лужа** — `AnomalyPuddles` (World): видимая, если под центром твёрдый пол; `Drain` списывает запас (60) при лечении (2 HP/с, `AnomalyExposure` → `VitalsEnvironment.PuddleHeal`), иссякшая или без пола — испаряется (облачко `DustFx`), за сессию. Свечение — слабый точечный свет, в освещённость не входит.
- **«Смотри на меня»**: вспышка-билборд (`AnomalyVisuals`), рябь в `VM_Distort` (вид 4). `Survival/AnomalyExposure`: ближайшая вспышка в конусе 70° и без стены (луч раз в 0.1 с) тянет взгляд (`PlayerLook.AddLook`, 60→15 °/с с расстоянием), взгляд в 12° — «смотрит»: рассудок −1.5/с, `VitalsModel.LookExposure` копится; 20 с — `StatusKind.Imprint` (максимум рассудка 50), 30 с без взгляда — сброс, 2 часа сна — снятие.
- **Шейдеры**: `AnomalyFx.hlsl` — пульсация (вид 3, мягкое радиальное «дыхание») и рябь (вид 4); `AnomalyVfx.shader` — лужа, вспышка, лучи (режим `_Mode`, материал `Fx_Anomaly.mat`, копии в рантайме).
- Отладка: `anomalies` (вид, класс, этаж), `goto_anomaly inverted|oasis|pulse|lookme|puddle`.

```
class LocalSession : INetSession   // одиночная игра: прямые вызовы
```
- **NetEntity** — компонент со стабильным `EntityId` (ulong) для всего, что синхронизируется: игроки, пропы, выпавшие предметы, враги, контейнеры.
- **Правило:** игровая логика **никогда не меняет общее состояние напрямую** из ввода, только через команду к авторитету. Это главное, что делает кооп добавляемым позже.
- Позже: `FishNetSession` или `NgoSession` реализует тот же интерфейс, транспорт — Steamworks.

### 5.1 Масштаб до 16 игроков
- **Лимит игроков** — параметр сессии (`maxPlayers`, по умолчанию 16), позже он появится в настройках сервера. Жёстко зашитых массивов «на 4 игрока» нет нигде.
- **Interest management:** клиент получает только сущности и правки мира в своём радиусе (колонны в `viewDistance`, сущности в `simulationDistance`). Без этого 16 игроков в разных концах мира забьют канал.
- **Нагрузка на хост:** стриминг и симуляция идут вокруг каждого игрока, поэтому 16 разбежавшихся игроков ≈ 16 активных областей. Меры: общий пул колонн с подсчётом ссылок, бюджет генерации на кадр с приоритетом по близости, более низкий `simulationDistance` для удалённых областей. Позже — опциональный **выделенный сервер** (headless-сборка того же кода: `INetSession` это позволяет).
- **Передача мира:** клиент запрашивает колонны у хоста. Нетронутую колонну клиент может сгенерировать сам по сиду (детерминизм), передаётся только сохранённая или изменённая. Это сильно экономит трафик.

## 6. Игрок и контроллер персонажа (VoidMall.Player)

Первый модуль, который мы реализуем.

### 6.1 Поток данных за тик
```
PlayerInputReader.Update (каждый кадр)
   ├─ PlayerLook.AddLook — взгляд крутится каждый кадр (отзывчивость при любом FPS),
   │                        с ограничением скорости поворота из модификаторов
   └─ копит нажатия кнопок до следующего тика
PlayerMotor.FixedUpdate (60 Гц) → IPlayerInputSource.ConsumeFrame()
   └─> PlayerInputFrame { Move, Yaw, Pitch, Held, Pressed }
PlayerMotor.Simulate(in PlayerInputFrame, dt)
   ├─ AggregateModifiers (все IMovementModifierSource + истощение стамины)
   ├─ Depenetrate → CategorizeGround (CapsuleCast вниз + снап)
   ├─ UpdateCrouch (проверка потолка перед вставанием, присед в воздухе поднимает ноги)
   ├─ Friction (если на земле) → Jump (буфер, койот-тайм, лимит скорости) → Accelerate | AirAccelerate + гравитация
   ├─ GroundMove: вдоль склона + перенос поверхностью → StepSlideMove (collide-and-slide, step-up) → StayOnGround
   ├─ PushRigidbodies, давление на проп под ногами
   └─ события: Landed(impactSpeed) + PlayerLandedEvent, Jumped; поправка взгляда StepOffset (интерполируется вместе с позицией)
PlayerCameraRig.LateUpdate: интерполяция, высота глаз, сглаживание ступенек, bob, landing dip, FOV, хромота, раскачка
```
- `MotorState` — простой struct (позиция, скорость, флаги земли, нормаль, crouch-фактор, ground velocity). `Simulate` — по сути чистая функция от состояния, ввода и физического мира. Это даёт **готовность к предсказанию и реконсиляции** и тестируемость.

### 6.2 KinematicMover
- Капсула: радиус 0,35, высота 1,8 (присед — 0,95, проходит в лаз 1 блок). Skin width 0,015.
- **Collide-and-slide:** до 4 итераций `Physics.CapsuleCast`. Скорость проецируется на плоскость удара, а при двух плоскостях — на их пересечение (как `ClipVelocity` у Source).
- **Step-up:** при ударе о стену на земле пробуем подняться на `stepHeight` (0,55 м), пройти вперёд и опуститься. Если результат дальше — принимаем.
- **Ground snap:** на земле после шага прижимаемся вниз до `stepHeight`, чтобы не «подпрыгивать» на спусках.
- **Склоны:** `maxSlope` 45°. Круче — считается стеной или скольжением.
- **Depenetration:** `Physics.ComputePenetration` против перекрытий (например, после ремеша чанка или телепорта).
- **Движущиеся поверхности** (эскалаторы, лифты, пропы под ногами): `IMovingSurface.GetVelocityAt(point)` добавляется к перемещению, при прыжке скорость наследуется.
- **Слои:** World, Props, Player, Enemy, Trigger, Debris. Мелкий дебрис игрока не блокирует.

### 6.3 SourceMovement (метры вместо юнитов, параметры в `MovementSettings` SO)
| Параметр | Значение по умолчанию | Аналог в Source |
|---|---|---|
| walk / run / sprint / crouch | 2.0 / 3.8 / 6.0 / 1.8 м/с | пропорции HL2, подбираются на плейтесте |
| groundAccelerate | 10 | sv_accelerate 10 |
| airAccelerate | 10, air wishspeed cap 0.6 м/с | sv_airaccelerate, 30 u |
| friction | 5, stopSpeed 1.9 | sv_friction 4–5, sv_stopspeed 100 |
| gravity | 15.2 м/с² | 800 u/s² |
| jumpHeight | 1.15 м (запрыгнуть на блок 1 м) | — |
| bhop-ограничение | трение при приземлении в первый тик, потолок горизонтальной скорости 1.25×sprint, стоимость прыжка в стамине | — |

### 6.4 Модификаторы движения
```
struct MovementModifiers {
  float speedMul, accelMul, jumpMul, staminaCostMul;
  float maxTurnRateDeg;     // ∞ по умолчанию; при перевесе, например, 90°/с
  bool  canSprint, canJump, canStand;
  float swayAmount, limpAmount;
}
interface IMovementModifierSource { void Apply(ref MovementModifiers m); }
```
- Агрегатор каждый тик собирает модификаторы от всех источников: `EncumbranceModifier` (Items), `InjuryModifier` (Survival), `StaminaModifier`, `ConsoleCheatModifier`.
- На этапе контроллера источники — заглушки с ползунками в debug-окне.

### 6.5 Стамина и урон от падения
- `IStaminaPool` (Core) — мотор вызывает `TryConsume`. Реализация живёт в Survival, на старте это простой пул.
- Событие `Landed(impactSpeed)` → Survival считает урон ногам: порог ~9 м/с, перелом — выше ~13 м/с.

### 6.6 Взаимодействие
- `Interactor` делает рейкаст от камеры (дистанция 2,5 м) к `IInteractable` (подсказка в HUD, F или Use).
- Захват пропов (`PropGrabber`): лёгкие держатся PD-регулятором (сила и момент к целевой точке перед камерой), тяжёлые тащатся через `ConfigurableJoint` или пружину от точки захвата. Масса влияет на скорость игрока через модификаторы.

### 6.7 Режимы
- `Noclip` и `Fly` — для консоли.
- `Seated` или `Focused` — режим ПК: мотор выключен, камера анимирована к монитору.

## 7. Пропы (`World/Props`, взаимодействие — `Game/PropInteractor`)
- `PropDef` (SO): форма процедурной модели и габарит (или своя модель `Mesh` + `Material`), масса, прочность, время разбора, выход материалов при разборе и при поломке, цвет пыли. `PropSet` — список пропов мира, `PropRegistry` — индексы и меши на сессию. Контейнеры и станции — этапы 6 и 10.
- **Расстановка** (`PropPlacer`): шаблон раздела по плану уровня, без пересечений и вне аномалий; каждый проп получает устойчивый ID (ячейка, уровень, номер). Это сборка той же генерации: тот же сид — те же пропы.
- **Стриминг** (`PropManager`): «корзины» (ячейка + уровень) на этаже игрока ±`world_prop_levels` в радиусе `world_prop_radius`, объекты из пула. Изменения за сессию — `PropState` по ID: сдвинутые («свободные») пропы стримятся по своей позиции, сломанные и разобранные не появляются, поврежденные помнят прочность. На диск — этап 9.
- **Сон:** спящий проп — статичный коллайдер без `Rigidbody` (тысячи стоят копейки). Просыпается, когда его берут, в него врезается движущееся тело или рядом меняется мир (выбили опору — `CellChanged`); успокоившись на секунду, засыпает (кинематика). Упавшие в пустоту исчезают.
- **Переноска** (в духе HL2): до `sv_hold_mass` (20 кг) — держится перед камерой (регулятор скорости и поворота, слой Debris — не толкает игрока), бросок, поворот на 45°, расстояние колесом; до `sv_drag_mass` (300 кг) — волочится силой в точке захвата с ограничением силы рук; тяжелее — не сдвинуть. Ноша — `IMovementModifierSource`: замедление, без спринта и прыжка при волочении.
- **Гвозди:** с молотком ПКМ прибивает ношу к тому, чего она касается. К миру — группа замирает (кинематика) с якорями в клетках (до 16); выломали все якоря — проп отрывается и падает. К другому пропу — группы сливаются в одно тело (коллайдеры детей входят в `Rigidbody` корня, масса суммируется). Удержание E — вытащить гвозди.
- **Поломка и разбор:** молоток снимает прочность; при нуле проп рассыпается пылью и обломками и даёт «сломанный» выход материалов. Удержание F — аккуратный разбор (дольше, полный выход). Пока нет инвентаря, выход пишется в журнал добычи (`PropSalvagedEvent`).
- **Сеть (позже):** авторитет — хост; клиент шлёт «взять/отпустить/прибить», хост симулирует и рассылает позы проснувшихся пропов.
- **Предметы на полках** (этап 6): «витринные» инстансы по якорям полки; при взятии — в инвентарь, при сбивании — физический `WorldItem`.

## 8. Предметы, инвентарь, крафт, навыки, выживание

### 8.1 Items
- `ItemDef` (SO): id, имя, описание, иконка, модель, **размер W×H**, вес, максимальный стак, категория, теги, `ItemComponents` (Food{fat, protein, carbs, water}, Tool{tier, blockDamage}, Weapon, Equippable{slot, layer: Armor|Clothing, armor по частям}, Container{gridW, gridH}, Placeable{propDef / materialDef}).
- `ItemStack` { defIndex, count, durability, `ItemInstanceData` для уникальных (магазин оружия, патроны внутри) }.
- `GridInventory` — чистая логика без Unity: `TryPlace(stack, x, y, rotated)`, `FindSpace`, `Move`, `Split`, `Merge`, вес. Покрывается EditMode-тестами.
- `Equipment` — слоты {Head, Torso, Arms, Legs, Feet} × {Armor, Clothing}. Плюс слоты рюкзака и разгрузки, которые задают размер сетки.
- `Hotbar` — 9 ссылок на ячейки инвентаря (не копии предметов).
- Все мутации — команды к авторитету (`MoveItem`, `DropItem`, `EquipItem`).

**Реализовано (этап 6, сборка `VoidMall.Items`):**
- `ItemDef` пока плоский SO (поля инструмента, еды, экипировки, контейнера, `PlacesBlock`/`SmoothMaterial`) вместо компонентов — разбить, когда появятся оружие и крафт. `ItemSet` → `ItemRegistry` (индексы `ushort`, `IItemCatalog` для сетки, кэш процедурных мешей `ItemMeshes`, блок-предмет на каждый ставимый материал).
- `GridInventory` — как описано выше, плюс `TryAdd` (сначала доложить в неполные стаки, потом место, остаток возвращается) и `TryConsume` (всё или ничего). Вложенный контейнер — `ItemStack.Contents`.
- `PlayerInventory` (на игроке): карманы 7×2, `Equipment`, `Hotbar`; подбор — сначала рюкзак, потом карманы; одежда и рюкзак сами надеваются в пустой слот; инструменты и блоки сами встают в хотбар. Слушает `MaterialMinedEvent`/`PropSalvagedEvent` (добыча в инвентарь, дальше 6 м — `WorldItem`). Вес → `MovementRules.ApplyEncumbrance` (`sv_carry_capacity`).
- `ShelfLoot`: у пропов есть точки спавна (`PropMeshes.GetItemSlots`). При появлении пропа: 15 % стеллажей пусты; заполненность стеллажа `lerp(0.25, 1.3)`; в каждой точке шанс «есть ли предмет» = `LootTable.Fill × заполненность × LootAmount мира × sv_loot_scale`, затем таблица раздела выбирает «какой» (до 3 попыток подобрать то, что влезает). Всё детерминировано от ID пропа; взятое и рассыпанное помнится за сессию. Отрисовка — `RenderMeshInstanced` группами по участкам 16 м с отсечением по кадру и `r_itemdistance`, без теней; выбор прицелом — луч по габаритам предметов.
- `WorldItems` — физические предметы на полу (пул, стриминг 40/48 м). Засыпают средствами PhysX и просыпаются от касания; при спавне из пула ставится и `Rigidbody.position`, иначе тело возвращает объект на старое место.
- Стеллажи, холодильники, паллетные стеллажи и вешалки — составной коллайдер по доскам (`PropMeshes.GetColliderParts`): сдвинутая или сбитая полка превращает товары в `WorldItem` ровно на своих местах, дальше — обычная физика.
- `Game/ToolController` — действия активного слота хотбара (руки, молоток, кувалда, лом, перфоратор, блоки, еда, экипировка, фонарик); `sv_creative` — блоки, гвозди и грунт не тратятся.
- UI: `UI/Game/CharacterWindow` (Tab), `HotbarHud`, `ItemVisuals`/`GridView`. Иконки — `Editor/ItemIconRenderer` (DrawMeshNow в RenderTexture шейдером `Hidden/VoidMall/ItemIcon`, без камер).

### 8.2 Crafting
- `RecipeDef`: ингредиенты, результат, время, станция (опционально), требуемый навык.
- `CraftQueue` на игроке (рецепты без станции) или на станции. Тикает в симуляции, ингредиенты резервируются при постановке в очередь.

**Реализовано (этап 8, сборка `VoidMall.Crafting`):**
- `RecipeDef` (SO): результат и количество, ингредиенты (`ItemAmount`), станция (`CraftStation` в Core: None — руки, Workbench, Sewing, Chemistry, Cooking), время, категория, `Blueprint` (открывается чертежом), навык и уровень. `RecipeSet` → `CraftingSystem` (на объекте мира рядом с ItemSystem). Ассеты — `Editor/RecipeAssetsSetup`.
- `CraftQueue` — чистая логика (тесты): до 8 `CraftJob`; ингредиенты списываются при постановке (`Taken` — вернуть при отмене), результат готов заранее (`Results`). Так же устроены починка (инструмент уходит на верстак, по готовности прочность 100%) и прогрев испорченного.
- `PlayerCrafting` (на игроке): очередь рук (идёт всегда, готовое — в инвентарь), изученные чертежи, проверки (`WhyCannotCraft`: чертёж, навык, станция, место, ингредиенты), бонусы навыков (время, «Экономный», «Прораб»). Чертёж — предмет с `TeachesRecipe`: ПКМ публикует `ItemConsumedEvent`, крафт учит рецепт; повторно не тратится (`PlayerInventory.UseBlockers`).
- `StationState` (по ID пропа, в `CraftingSystem`, переживает выгрузку пропа): своя очередь, выдача 6×3, топливо (секунды), занятость (`Occupant` — «Станция занята»). Верстак, швейный, химстол тикают только при открытом окне; плита и горелка (`PropDef.StationAutonomous`) — сами, пока есть топливо (`ItemDef.FuelSeconds`). Станцию сломали — выдача и ингредиенты очереди падают на пол.
- Станции в мире: `SectionDef.Station`/`StationChance` → `PropPlacer` ставит станцию у стены. Предметы-постройки (`ItemDef.PlacesProp`) ставятся призраком (`ToolController`: R — поворот, ПКМ — поставить); пропы, созданные игроком (`PropManager.IsPlayerMade`), не получают лут полок.
- Износ: `ItemDef.Uses` (удар, применение бура, секунда горения факела), `PlayerInventory.Wear`; починка — `ItemDef.RepairCost`, `Electric` требует «Техник» 1.
- UI: `CraftPanel` (общая для вкладки «Крафт» и `StationWindow`), `SkillsPanel`.

### 8.3 Skills
- `AspectDef` (Физические, Умственные, Строительные, Боевые, Выживание), `SkillDef` (аспект, стоимость, требования, эффекты-модификаторы).
- `SkillProgress`: очки по аспектам. Начисление — по событиям (`BlockBroken`, `ItemCrafted`, `DistanceSprinted`…) через таблицу правил.

**Реализовано (этап 8, сборка `VoidMall.Skills`, ссылается только на Core и Console):** `SkillCatalog` (аспекты, 17 навыков по 3 уровня, цена 3/6/10, требования), `SkillTree` — чистая модель (очки копятся дробно, тратятся целыми, сброс возвращает очки), `PlayerSkills` (на игроке; `LevelOf`/`AwardLocal` — статические, без игрока уровень 0). Эффекты применяют системы выше: инвентарь (Грузчик, Аккуратный разбор), выживание (`VitalsPerks`), крафт, инструменты (Разрушитель, Плотник). Очки: `Game/SkillRules` (ходьба, спринт, переноска, ломание рядом), крафт, стройка, гвозди, разбор, еда, лечение, сон, холод — там, где происходит действие.

### 8.4 Survival
- `BodyParts` — HP по 7 частям. `StatusEffect` (SO + runtime-экземпляр): кровотечение, перелом, боль, инфекция и т.д., с тиками и снятием предметами.
- `Nutrition` (жиры, белки, углеводы, вода), `Thermal` (температура тела против зоны), `Stamina`.
- `Rest` (бодрость): сон на `BedProp` или `SleepingBag` (это ещё и точка респауна). В кооперативе время суток не ускоряется, сон просто восстанавливает бодрость быстрее **[решим при коопе: ускорять ли время, если спят все]**.
- `Sanity` (рассудок): скорость изменения = f(освещённость в точке игрока §4.8, бодрость, нахождение в объёме аномалии, ночь). Эффекты низкого рассудка — `HallucinationDirector` на **клиенте** (ложные манекены, звуки, пост-эффекты). Галлюцинации локальны и по сети не синхронизируются.
- Все они реализуют `IMovementModifierSource` и/или дают модификаторы статов.

**Реализовано (этап 7, сборка `VoidMall.Survival`):** решение этапа — одно здоровье + травмы-состояния, части тела не делаем.
- `VitalsModel` — чистая логика без сцены (покрыта EditMode-тестами): здоровье, сытость (ккал), вода, бодрость, рассудок, температура тела, стамина; список хранимых `Status` (кровотечения, переломы с шиной, боль, инфекция, отравление, обезболивающее, `NearDeathTrauma` со стеками) + вычисляемые состояния для UI (`GetConditions`, тексты — `StatusCatalog`). Потребности и заживление идут в **игровых часах** (сон ускоряет время), кровотечение, температура и рассудок — в реальных секундах. Рацион — окно 24 игровых часа. `ApplyModifiers` переводит травмы в `MovementModifiers` через `MovementRules`.
- `PlayerVitals` (на игроке мира, порядок −40): тикает модель, раз в 0,5 с собирает `VitalsEnvironment` (температура — `SurvivalEnvironment`, свет — `ILightProbe`, тепло надетой одежды `ItemDef.Warmth`, аномалия); подменяет пул стамины мотора (`PlayerMotor.SetStaminaPool`) и даёт модификаторы движения. Урон: `PlayerLandedEvent`, `DebrisImpactEvent`, `PlayerImpactEvent` (летящий проп, `PropBody`), порезы (`Cut` из `ToolController`), глитч (`InMarker(Glitch)` раз в 2 с — `SetHealth(random)`), пустота (`PlayerFallGuard` → `Kill(Void)`). Еда и лекарства — `ItemConsumedEvent`; бесполезное лекарство не тратится (`PlayerInventory.UseBlocker` → `WhyUseless`).
- Сон: `TrySleep(PropBody)` на пропе с `PropDef.Sleepable` (кровать, спальник) — точка возрождения (ID пропа + позиция), ввод — контекст `Menu`, `WorldClock.TimeScale = sv_sleep_speed`. Будит урон, полная бодрость или E.
- `VitalsEffects` — глобальный URP Volume из кода (виньетка, зерно, хроматическая аберрация, искажение линзы, насыщенность): рассудок, ранение, глитч, холод, смерть.
- UI: `UI/Game/VitalsHud` (полоски, плашки, экраны сна и смерти, метка сумки), вкладка «Состояние» в `CharacterWindow`.

### 8.5 Смерть и респаун
- При смерти авторитет создаёт `DeathBackpack` (контейнер-сущность с `NetEntity`) и переносит туда предметы по правилу `WorldSettings.deathDrop` (Nothing / Hotbar / Backpack / All). Маркер рюкзака виден на компасе владельца.
- Точка респауна: последняя кровать или спальник игрока (`SpawnPointRegistry`, сохраняется в сейве игрока), иначе — случайная безопасная точка в радиусе R от места смерти (проверки: на полу, есть место под капсулу, не в аномалии).
- Дебафф `NearDeathTrauma` — обычный `StatusEffect` со стеками.

**Реализовано (этап 7):** смерть — сумка `item.lost_bag` (контейнер 12×12, `UnpackOnPickup`: при подборе содержимое раскладывается по инвентарю) создаётся на месте гибели как `WorldItem`, правило — `sv_death_drop` (0 ничего / 1 хотбар / 2 рюкзак / 3 всё); в пустоте — на последнем безопасном месте. Возрождение через 3 с: у кровати, если её проп не удалён (`PropManager.IsRemoved`), иначе случайная точка пола в 5–25 м (луч вниз, место под капсулу, не в аномалии). До сохранений (этап 9) точка возрождения живёт только в сессии.

## 9. Бой и ИИ
- `IDamageable` + `DamageInfo{amount, type, bodyPart, source, impulse}`. Хитбоксы по частям тела у игрока и врагов.
- Оружие: `WeaponDef` (ItemComponent) плюс runtime-логика (стрельба рейкастом, перезарядка, разброс от модификаторов). Ближний бой — sweep-кастом.
- ИИ: простая FSM или utility-AI. Восприятие: зрение (конус и рейкаст), слух (события шума с радиусом).
- **Навигация** по изменяемому миру: runtime NavMesh тайлами вокруг игроков (`NavMeshBuilder.UpdateNavMeshDataAsync` с источниками из мешей чанков), переобновление тайла после `WorldChanged`. Если будет дорого — своя A* по сетке клеток (мир клеточный, это естественно). Решение принимаем на этапе ИИ.
- **Манекен** (единственный враг на старте): состояние `Frozen` / `Moving`. Каждый тик авторитет проверяет, **видит ли его хоть один игрок**: манекен в конусе камеры игрока, линия видимости не перекрыта (рейкаст к 2–3 точкам тела) и **освещённость** в его точке выше порога или он в луче фонарика игрока (см. §4.8). Если не видит никто — манекен двигается к цели. Для 16 игроков проверка дешёвая: сначала отсев по дистанции и конусу, рейкасты только для прошедших.
- Враги — это данные `EnemyDef` (SO) плюс компоненты поведения, чтобы новые враги добавлялись в основном контентом.

## 10. UI (UI Toolkit)
- Один `UIDocument` на экран (HUD, CharacterWindow, Console overlay, Pause) с общей темой (USS-переменные).
- `CharacterWindow` — табы (Инвентарь/Навыки/Крафт/Состояние), каждая вкладка — отдельный контроллер.
- Инвентарь-сетка — кастомный `VisualElement` с собственной отрисовкой (`generateVisualContent`) и drag & drop. Для геймпада — курсор по ячейкам (D-pad или стик, A — взять/положить, Y — повернуть).
- **ОС ПК:** **world-space UIDocument** на мониторе (поддерживается в Unity 6.x). Ввод мыши — рейкаст по монитору, геймпада — виртуальный курсор и фокус-навигация. Если world-space окажется ограничен — fallback: `PanelSettings.targetTexture` + `SetScreenToPanelSpaceFunction`.
- **Консоль:** один `ConsoleView` (VisualElement) используется и в окне приложения cmd на ПК, и в оверлее `~`.
- Ввод: action maps `Player`, `UI`, `PC`, `Console`. Переключает их `InputContextStack` (верхний контекст забирает ввод).

## 12. Лобби и портал (VoidMall.Lobby)
- Сцены: **Boot** (постоянная, сервисы), **Lobby** (аддитивная, «карман» далеко от origin, например y = −10000 или отдельный offset), **World** (аддитивная, контейнер для чанков).
- `PCTerminal` — взаимодействие F, анимация камеры к монитору, переключение ввода на контекст `PC`.
- **WorldSession lifecycle:** `Configure → Generate/Load (стриминг вокруг spawnPoint) → Ready (спавн-регион смешен и с коллайдерами) → Portal opens → Player crosses → Portal closes after T → Lobby scene unloaded`.
- **Портал:** пара `PortalEndpoint` (лобби и мир). Камера портала повторяет позу игрока относительно портала и рендерит в RenderTexture с наклонной ближней плоскостью (oblique near plane). Плоскость портала сэмплит текстуру в экранных UV. При пересечении плоскости (проверка в фиксированном тике по знаку) игрок, его скорость и взгляд трансформируются в мир, а камера портала меняется местами, чтобы не было кадра-вспышки.
- Портал в мире сохраняется как структура до закрытия.

## 13. Сохранения (VoidMall.Save)
```
%userprofile%/AppData/LocalLow/<company>/VoidMall/Saves/<WorldName>/
  world.json        — имя, сид, WorldSettings, generatorVersion, contentVersion, время, превью-путь
  registry.json     — ID ↔ индекс для материалов и предметов на момент сейва
  players/<id>.json — позиция, состояние, инвентарь, навыки, статусы
  regions/r.<x>.<z>.bin — 32×32 колонны: заголовок со смещениями + сжатые колонны
  preview.png
```
- **Сохраняются все посещённые колонны целиком**: клетки (палитра + RLE, затем Deflate/Brotli), пропы (`PropState`), содержимое контейнеров, выпавшие предметы, враги в состоянии сна.
- Запись — в фоновом потоке со снапшотом данных. Автосейв по таймеру и при выгрузке колонны.
- Миграции: `contentVersion` и `registry.json` позволяют переназначить индексы после обновления контента.

## 14. Производительность (бюджеты — цель)
| Что | Бюджет |
|---|---|
| Генерация + мешинг колонны (4 чанка, из них ~2–3 непустых) | < 8 мс суммарно в джобах, < 0,5 мс главного потока |
| Ремеш после правки | результат виден на следующем кадре (< 16 мс) |
| Кадр (средний ПК) | 60+ FPS при viewDistance 8 |
| GC-аллокации в тике | 0 в мире и моторе |

Профилировать с Profiler-маркерами по модулям с первого дня.

**Замеры и правила (сделано):** `Perf.Register/Measure` (Core) — метка системы: время и рост управляемой кучи за кадр, видна и в Unity Profiler. `PerfMonitor` (Game) пишет кадры и отчёт: `perf_run [м] [м/с] [задержка]` — забег по прямой, `perf_record [с]` — запись, пока бегаешь сам, `perf_markers [фильтр]` — какие метки Unity есть; отчёт — в консоль и `Temp/VoidMallPerf.txt`. Правила, найденные замерами:
- Тяжёлая работа при подгрузке — порциями с бюджетом времени на кадр: появление и выгрузка пропов (`world_prop_budget_ms`), подключение мешей и коллайдеров чанков (`world_apply_budget_ms`), структуры — по одной части за кадр.
- Основной поток не ждёт фоновые задачи (`JobHandle.IsCompleted`); перед выгрузкой чанков новые задачи не ставятся, пока текущие не доделаны.
- Одинаковые меши строятся один раз (кэш в `StructureFactory`).
- Спящие пропы выключены (`enabled = false`): Unity не вызывает их FixedUpdate, события столкновений приходят и выключенным.
- Неподвижные коллайдеры не двигать после включения: проп настраивается в выключенном пуле и включается на месте.
- Товары на полках пересобираются по участкам 16 м, а не целиком.

Забег 600 м на 9 м/с (редактор, Ryzen 5 3600 / RTX 3060): средний кадр 27,8 → 17,5 мс, кадров дольше 33 мс 398 → 17, мусор 82 → 22 КБ за кадр.

## 15. Тесты и качество
- **EditMode:** формулы SourceMovement, GridInventory, CraftQueue, генератор (детерминизм: одинаковый сид дважды → одинаковый хеш чанка), сериализация туда-обратно.
- **PlayMode:** мотор в greybox-сцене (ступеньки, склоны, потолок при вставании, лаз 1 блок, движущаяся платформа), стриминг без дыр, сейв/загрузка.
- **Debug-инструменты:** оверлей движения (скорость, состояние, модификаторы), визуализация чанков и их состояний, гизмо структур генератора.
- **Код:** C# 9, `namespace VoidMall.<Module>`, PascalCase, `_camelCase` для приватных полей, без `Find`/`SendMessage`, без `Update` там, где хватает событий или тиков.
- **Перезагрузка домена при входе в Play отключена** (Enter Play Mode Options). Любое статическое состояние (поля, события, синглтоны) обязано сбрасываться в методе с `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` — см. `Services`, `EventBus`, `DevConsole`, `PlayerMotor.Local`.
- **Настройка проекта воспроизводима:** меню **Void Mall/Setup** создаёт слои, ассет ввода, PanelSettings, конфиг, материалы, префаб игрока и полигон. Тесты запускаются из **Void Mall/Tests** (отчёт в `Temp/VoidMallTestResults.txt`).
- **Контроль версий:** проект сейчас **не в git**. Рекомендую `git init` с Unity `.gitignore` и Git LFS для бинарных ассетов перед стартом кода.
